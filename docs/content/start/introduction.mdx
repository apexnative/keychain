`@apexnative/keychain` keeps an app's secrets where the platform keeps its own: in the Keychain <Os name="iOS" /> and under keys of the Android Keystore <Os name="Android" />. Tokens, passwords and encryption keys go in by key and come out by key; a value can be locked behind Face ID, a fingerprint or the device passcode, and the operating system checks it.

```ts title="session.ts"
import { AccessControl, createKeychain, keychain } from '@apexnative/keychain';

// The default keychain: no prompt, readable in the background.
await keychain.setItem('accessToken', accessToken);

// A vault that opens with the biometrics enrolled today.
const vault = createKeychain({
  service: 'vault',
  accessControl: AccessControl.BiometryCurrentSet,
  prompt: { title: 'Unlock your account' },
});

await vault.setItem('refreshToken', refreshToken); // no prompt
const token = await vault.getItem('refreshToken'); // Face ID, then the value
```

The write never shows a prompt. The read shows the system prompt, and the value comes back only when the user passes it. The [Quick start](./quick-start) builds this step by step.

## Why another keychain package {#why}

React Native has two common answers for secure storage, and both leave gaps.

`react-native-keychain` is the standard, but its last release is from March 2025 and its architecture predates the New Architecture: the TurboModule spec types every parameter as `Object`, and Android still runs a separate old-architecture module. Its API is built around one username and password per service, so a token or a key has to borrow the service as its name. On Android, a request for biometrics on a device without them quietly stores the value without protection.

`expo-secure-store` has the friendlier key/value model, but one switch for security (`requireAuthentication`), errors without codes, a changed fingerprint set that reads as `null`, and a synchronous API that can block the JS thread on a prompt.

This package keeps the key/value model, adds bytes and credentials, and makes the security options mean the same thing on both platforms.

<Thesis eyebrow="The idea in one line">
  Biometrics is a <Mark>lock on the value</Mark>, not a <Mark>yes from JavaScript</Mark>.
</Thesis>

A check that shows Face ID and returns `true` lives in your app's code, and on a compromised device the answer can be changed while the token sits unprotected. Here the operating system encrypts the value with a key that works only after the user passes the prompt; without it, the value can't be decrypted at all. [How biometrics works](../fundamentals/biometrics) explains the details.
